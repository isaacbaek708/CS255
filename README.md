# CS255
CS 255 Portfolio Reflection
DriverPass Project Summary

The DriverPass project was based on a client named DriverPass. DriverPass wanted a system that would help students prepare for their driving tests by giving them access to online practice exams, online training materials, and on-the-road driving lesson scheduling. The system also needed to support different users, including customers, instructors, office staff, the owner, and the IT officer. The goal of the project was to collect the client’s requirements and design a system that would meet their business needs.

What I Did Well

One part of the project that I think I did particularly well was identifying the main needs of the client and organizing them into clear requirements. I focused on what DriverPass wanted the system to do, such as allowing customers to schedule lessons, take practice exams, choose packages, and track their progress. I also made sure to consider different user roles and what each user would need to access in the system.

What I Would Revise

If I could revise one part of my work, I would improve the diagrams in the system design document. I would make them more detailed and cleaner so that they are easier for both technical and nontechnical users to understand. I would also make sure the relationships between users, system actions, and data were labeled more clearly. This would help the design communicate the system’s purpose more effectively.

Interpreting and Implementing User Needs

I interpreted the user’s needs by reviewing the DriverPass interview information and identifying what each type of user needed from the system. For example, customers needed to create accounts, schedule lessons, take practice tests, and view progress. Staff members needed to manage appointments and customer information. The IT officer needed access to manage accounts and security. I used these needs to guide the requirements and diagrams in my design. Considering user needs is important because a system is only successful if it solves the actual problem for the people who use it. If the design does not match user needs, the final system may be confusing, incomplete, or not useful.

My Approach to Software Design

My approach to designing software is to first understand the client’s problem and gather clear requirements. After that, I break the system into smaller parts, such as users, functions, processes, and data. I use diagrams like use case diagrams, activity diagrams, sequence diagrams, and class diagrams to organize the design and show how the system should work. In the future, I would continue using interviews, requirement lists, process models, and object models to analyze and design systems. These strategies help make sure the system is planned clearly before development begins.
